# 简历事实契约

本契约是 `resume-builder` 与 `jd-tailorer` 共用的底层事实边界与数据契约。它规定简历可以记录什么、如何记录证据、字段定义与准入门槛。它不替代 HTML 模板，也不决定视觉样式；具体写作手法、表达公式与板块建议详见配套文档 [`content-writing.md`](content-writing.md)。

---

## 一、不可逾越的事实边界

- **证据为王**：只使用候选人明确提供、现有简历明确写出，或候选人可核验材料明确支持的事实。
- **改写边界**：改写只能改变表达清晰度、行文顺序、叙述粒度和与 JD 的术语对齐，不得新增或推断雇主、职位、日期、学历、技能、数字、成果、职责、奖项或用户/业务规模。
- **JD 属性隔离**：JD 中的要求、关键词和公司描述属于目标岗位信息，绝不是候选人事实。不能因为 JD 提到某项技术，就把它写进候选人的技能或经历。
- **禁止脑补指标**：严禁用“听起来合理”的数字填补空白。没有可信来源的数字必须追问、标记为未验证，或从最终输出中剔除。
- **置信度边界**：`confidence` 反映事实被当前证据支持的程度，不等于允许代理猜测；低置信度内容不能以确定口吻输出。
- **隐私保护边界**：不确定的个人隐私字段默认不收集、不展示；若用户明确要求展示，也应先确认准确性、用途和投递范围。

## 二、简历数据结构与字段定义

简历母版仅可包含以下 8 个标准板块；没有事实支撑的板块保持为空，不用占位内容凑数。`resume-builder` 和 `jd-tailorer` 必须使用这里的 `section` 枚举检查每条 claim：

| 板块 | 允许记录的内容与边界 |
|---|---|
| `profile` | 姓名、联系方式、所在地、求职意向、个人链接，以及用户确认需要展示的工作授权信息 |
| `education` | 学校、专业、学历、时间、成绩、课程、学术活动；仅写用户能确认的内容 |
| `experience` | 实习、工作、研究或其他正式经历中的组织、角色、时间、行动、产出和结果 |
| `projects` | 课程、个人、开源、研究或竞赛项目中的角色、范围、技术、交付物和结果 |
| `campus` | 校园组织、学生工作、志愿服务、社团、校园活动等经历中的组织/活动、角色、时间、行动、交付物和结果 |
| `skills` | 用户实际使用或明确掌握的技术、工具、语言、方法和能力；熟练度必须有用户依据 |
| `awards` | 奖项、竞赛、证书、荣誉、级别、授予方和时间；不得把参与写成获奖 |
| `summary` | 由上述已验证事实归纳出的职业定位、相关能力和求职方向，不引入新事实 |

每条对外可见的陈述都视为一个 `claim`。在采集与分析阶段按以下标准结构保存与检查；未具备必要字段的事实不得进入最终简历：

```yaml
section: experience        # profile/education/experience/projects/campus/skills/awards/summary
claim: "优化数据查询流程并完成上线交付"
source: user               # user/resume/artifact/derived
confidence: high           # high/medium/low
evidence:
  - "候选人说明其负责查询流程优化"
  - "候选人提供上线记录或可核验项目材料"
metric_status: verified    # verified/estimated/unverified/not_applicable
```

### 私有事实文件

在项目目录外的用户私有工作区，将全部已确认 claim 保存为 `resume-facts.yaml`；以 [`resume-facts.example.yaml`](resume-facts.example.yaml) 为最小结构。它是母版和 JD 定制版的唯一事实源，HTML/PDF 只是由它生成的交付物。

- `claims`：仅保存通过用户确认、允许进入最终简历成稿的事实。
- `pending_claims`：记录从旧简历、JD 分析或改写交互中发现的待确认字段；**绝对不得进入最终成稿**。
- 每个确认后的 claim 记录 `confirmed_at`；若用户更新或撤回事实，应就地更新该记录，而不是静默改写历史定制版。

### 核心字段权威定义

- `source`（事实来源）：
  - `user`：候选人直接陈述或明确确认；
  - `resume`：候选人已有基础简历原文；
  - `artifact`：作品、代码仓库、成绩单、证书、上线记录等可核验实物材料；
  - `derived`：仅表示对已有已证实事实的保守归纳（如 summary），不能表示新事实来源。
  - *注：JD、市场文章和模板示例绝不得作为候选人事实来源。*
- `confidence`（置信度）：
  - `high`：来源清晰、明确且前后一致；
  - `medium`：有来源但存在细节模糊，需候选人复核；
  - `low`：来源不详、可能过时或存在冲突。`medium/low` 内容在输出前必须回访确认。
- `evidence`（证据线索）：
  - 能合理解释“为什么可以这样写”的原始记录、材料线索或核验依据。严禁将改写润色后的句子本身当作证据。
- `metric_status`（指标核验状态）：
  - `verified`：数字、比例、时间、范围等量化指标有明确可信来源；
  - `estimated`：仅适用于候选人明确说明为估算、并同意按估算呈现的情况（需带“约/估算”限定）；
  - `unverified`：待确认指标，禁止直接写入最终成稿；
  - `not_applicable`：定性陈述，无适用的数字指标。

## 三、改写硬性约束

在进行文字润色和岗位对齐时，必须遵循以下硬性契约（具体写作结构与技巧见 [`content-writing.md`](content-writing.md)）：

1. **事实先行**：先剥离背景、角色、行动、交付物与结果事实，再组织语句；不得把“职责”自动升级为“成果”。
2. **证据多维化**：优先核验量化指标；无可靠数字时，必须使用经过确认的真实角色（主导/独立/协作）、交付物、质量状态、时间节点等客观证据，严禁编造数据。
3. **JD 对齐隔离**：`jd-tailorer` 仅允许在已有事实 claim 范围内重排与对齐术语，关键词必须标注来源（详见 `content-writing.md`），无法匹配的岗位要求必须如实列为缺口，禁止凭空制造匹配。
4. **归纳克制**：`summary` 必须是对已有板块事实的客观归纳，禁止捏造“精通”“资深专家”等无证据的自评。
5. **多模式一致性**：在视觉 HTML/PDF 与 ATS-safe 模式之间切换时，只改变排版呈现，不得更改事实、证据状态或未验证标记。

---

## 四、输出前的最小门槛

一个 claim 只有同时满足以下全部条件，才能进入最终简历：

1. 具备合法的 `source` 与可理解的 `evidence`；
2. `confidence` 不为 `low`，或已获得候选人明确确认；
3. 若包含量化指标，`metric_status` 必须为 `verified`，或明确标注为候选人认可的 `estimated`；
4. 改写没有引入来源中不存在的新实体、数字、因果关系或能力等级；
5. 若用于 JD 定制，使用的关键词能追溯到 JD 或候选人已有材料。

> **待确认字段唯一处理规则**：
> 凡不满足上述门槛的内容，必须归入 `pending_claims`（待确认字段清单），**绝对不得以任何推测口吻进入最终简历成稿**（包括视觉 HTML/PDF 与 ATS-safe HTML/PDF）。待确认字段仅允许出现在采访采集记录、匹配分析报告等交互分析文档中。
